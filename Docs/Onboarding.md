# Onboarding

Everything a programmer needs to go from a fresh clone to a merged change: setup, how the code is laid out, how a
frame of UI actually gets from gameplay to the screen, how to make the common kinds of change, and how changes are
verified. It links to the detailed documents rather than repeating them; read it once top to bottom, then use it as a
map.

## Your first hour

### Prerequisites

| Tool | Why |
|---|---|
| Unreal Engine **5.8** (installed or source build) | The project's engine (`MVVMSample.uproject`: `EngineAssociation` 5.8) |
| Visual Studio 2022 or Rider with the UE C++ workload | Building the `MVVMSample` and `MVVMSampleTests` modules |
| **Git LFS** | Every `.uasset`, `.umap`, `.png`, `.ttf` and `.locres` is stored in LFS (`.gitattributes`); without it you get pointer files |
| Python 3 on `PATH` | The test runner, translation check, profiling diff and localization helpers |
| Windows PowerShell 5.1 | The gate (`Verify.ps1`), screenshot capture and profiling scripts |

### Clone and point the scripts at your engine

```bash
git lfs install
git clone <repository> MVVMSample
cd MVVMSample
git lfs pull
```

Every script finds the engine and the project through `Scripts/Paths.cfg` (default `EngineDir=D:\UnrealEngine\UE_5.8\Engine`).
If your engine lives elsewhere, do not edit that file: create `Scripts/Paths.local.cfg` (not committed) with only the
keys you change:

```ini
EngineDir=C:\Program Files\Epic Games\UE_5.8\Engine
```

### Build, open, play

```bash
"<EngineDir>\Build\BatchFiles\Build.bat" MVVMSampleEditor Win64 Development -Project="<repo>\MVVMSample.uproject" -WaitMutex
```

Or open `MVVMSample.uproject` and let the editor compile. The default map is `L_Arena` (a generated night rooftop with
five clues and training-dummy thugs) and the game mode is `AMvsGameMode`; press Play. The controls are in the
[README](../README.md#run-it); all of them are rebindable under Pause > Settings > Controls.

After adding, moving or deleting a source file, regenerate the project files so the IDE sees it:

```bash
"<EngineDir>\Build\BatchFiles\Build.bat" -projectfiles -project="<repo>\MVVMSample.uproject" -game -engine
```

### Run the tests

Close the editor first (the scripts launch their own instances).

```bash
python Scripts/run_tests.py                       # everything: editor pass, then game pass
python Scripts/run_tests.py Mvs.Settings          # one group (editor pass only)
python Scripts/run_tests.py Mvs.Functional.Pause  # one functional test (game pass only)
```

The game pass opens a small game window and drives it through Slate's input path; it does not need the window focused,
but it does need the machine otherwise idle enough not to move the mouse over it.

If all 65 tests pass you have a working setup. The last step of onboarding is running [the gate](#verifying-a-change-the-gate)
once, so you know what a passing change looks like.

## What the project is

A small third-person combat and investigation sandbox whose deliverable is the **UI layer**: C++ view models on the
MVVM plugin, a Common UI layer stack, custom Slate widgets, a forensic post-process, accessibility, localization and
rebinding, with automated tests and measured performance. Gameplay is deliberately thin: the engine mannequin, five
clues to scan, a few thugs that telegraph attacks for the counter prompt.

Everything in the game is code-built: input assets, HUD, menus, the arena (generated by a Python script). The only
designer-authored UI assets are `WBP_ClueEntry` (the case-file tile class) and `WBP_PauseMenu` (the pause screen's
status panel, built with MVVM View Bindings to prove the designer path). The `ThirdPerson` and `Variant_*` content
folders are the engine template's and are not used by the sample (their strings are excluded from localization).

## The one rule

**Gameplay never knows the UI exists, and widgets never change gameplay state directly.**

```text
Gameplay components ──native delegates──▶ binders ──▶ view models ──field notify──▶ widgets
        ▲                                                  │
        └──────────────── commands (RequestUse, …) ────────┘   ◀── input actions / clicks
```

- Gameplay (`Gameplay/`) includes no UI header.
- View models (`ViewModels/`) hold presentation state and commands; they reference no widget and no world, so tests
  construct them directly.
- Widgets (`UI/`) read view models and send commands to them; they never touch a component.
- The glue is one binder per feature, owned by `UMvsViewModelSubsystem` (one per local player).

Every design decision below follows from that rule. The layer table with what may depend on what is in
[Architecture](Architecture.md#layers).

## How it runs: from Play to a menu

Follow this once in the debugger; it is the fastest way to learn the codebase.

1. **Game mode.** `AMvsGameMode` uses `AMvsCharacter` as its default pawn and spawns the thugs (`SpawnThugs`, from
   `ThugSpots`).
2. **Input** (`AMvsPlayerController::SetupInputComponent`):
   - `BuildInputAssets` creates every input action and the gameplay mapping context from `MvsActions::GetTable()`, and
     marks the rebindable ones (ADR 0005). The gameplay context and the menu context (`UMvsUIInputData`) are both added;
     both stay on.
   - Gameplay actions are bound to handlers; the keys that open screens are bound from the shortcut table
     (`UMvsUISettings::GetShortcuts`) to `OnShortcut`.
3. **UI** (`AMvsPlayerController::BeginPlay`): `RegisterRebindableContext` hands the context to Enhanced Input's user
   settings; `UMvsUISubsystem::EnsureLayout` creates the primary layout (Game, GameMenu, Menu, Modal stacks) and starts
   loading every screen class asynchronously; the HUD class is loaded synchronously and pushed onto the Game layer.
4. **Possession** (`OnPossess` / `AcknowledgePossession`). `BindViewModelsToPawn` calls `UMvsViewModelSubsystem::BindToCharacter`: each binder subscribes to
   its feature's components and pushes their current state into its view models.
5. **The HUD constructs** (`UMvsHudWidget`): health bar, gadget selector, combo, objective tracker, subtitles, damage
   vignette, Forensic overlay, clue markers and threat indicators. Each finds its view model through the subsystem and
   binds the fields it shows with `MvsMVVM::Bind`.
6. **A key opens a screen.** Pressing Esc fires the `Pause` action; the controller calls
   `UMvsUISubsystem::HandleShortcut("Pause")`, which looks the action up in the shortcut table (pause: open or back) and
   pushes `UMvsUISettings::PauseMenuClass` (today `WBP_PauseMenu`) onto the Menu layer. Common UI switches to Menu input
   mode, so gameplay keys stop reaching the game; from here the screen's own bindings answer keys.

### One value, end to end: taking damage

```text
UHealthComponent::ApplyDamage
  └─ OnHealthChanged(Health, MaxHealth) (native delegate)
       └─ UMvsVitalsBinder  (subscribed in BindToCharacter, through FMvsSubscriptions)
            └─ UPlayerVitalsViewModel  (UE_MVVM_SET_PROPERTY_VALUE: field notify fires only on change)
                 └─ UHealthBarWidget handler (bound with MvsMVVM::Bind to the fields it shows) → repaints
```

### One command, end to end: using a gadget from the wheel

```text
Wheel segment chosen (SGadgetWheel) → UGadgetWheelScreen
  └─ UGadgetBarViewModel::RequestUse(slot)          (the view model's command: broadcasts OnUseRequested)
       └─ UMvsGadgetBinder → UGadgetComponent::UseGadget(slot)   (the binder hands it to gameplay)
            └─ OnGadgetUsed / OnCooldownChanged → binder → UGadgetSlotViewModel → HUD slot and wheel update
```

## The systems you will touch

Each has a short summary here; the detail is in [Architecture](Architecture.md) and the linked ADR.

### View models and binding (ADR 0001, 0008)
- View models derive `UMVVMViewModelBase`; every displayed property is `FieldNotify` with a getter, set through
  `UE_MVVM_SET_PROPERTY_VALUE` so notifications fire only on a real change.
- Code-built views subscribe with `MvsMVVM::Bind(ViewModel, this, &Handler, { Fields })` and `MvsMVVM::Unbind` in
  `NativeDestruct`. Designer-built views use the plugin's View Bindings with `UMvsViewModelResolver`, which hands a
  widget its owning player's view model by class.
- Find a view model with `UMvsViewModelSubsystem::Get<T>()` (or the typed getters) on the owning local player.
- `FText` fields: `UE_MVVM_SET_PROPERTY_VALUE` compares with `IdenticalTo`, which treats every freshly formatted text as
  new and every localized text as unchanged after a language switch. Compare by display string where that matters, as
  `USettingRowViewModel` does.

### The UI layer stack and screens (ADR 0003, 0007)
- Four stacks: **Game** (HUD), **GameMenu** (in-world overlays such as the gadget wheel), **Menu** (pause, settings,
  controls, case file), **Modal** (confirmations). Only `UMvsUISubsystem` pushes and pops.
- Every menu derives `UMvsScreen`: Menu input config, Common UI back handling, default focus, `BuildMenuFrame` (blur,
  scrim, title, slide-in) and builders for text, menu items and the action bar.
- Screen classes are settings (`Project Settings > Game > Mvs UI`), so a designer's Widget Blueprint can replace one
  without code. They are preloaded; `UMvsUISettings::Resolve` warns if one is ever loaded on the spot.
- Keys that open screens are data: `UMvsUISettings::GetShortcuts` (action, layer, screen setting, behaviour: open or
  back / toggle / hold). The base screen derives its own closing key and the other screens' toggle keys from it.
- The prompt row is a bound action bar of `UMvsHintButton`s: each shows the current device's key and is clickable.

### Input (ADR 0005, 0007)
- One table, `Input/MvsActionTable.cpp`, defines every gameplay action: name, display text, value type, default
  keyboard and gamepad keys, rebindable. No input assets exist on disk.
- Rebinding goes through Enhanced Input's user settings (`IMvsBindingStore`; memory in tests). Rebind names are saved,
  so renaming an action loses players' rebinds (a characterization test pins the names).
- Glyphs (`UMvsInputGlyph`) show the key Common UI resolves for the current device and update on device switch.

### Settings, theme and accessibility
- `FMvsSettingsData` is a plain struct saved in GameUserSettings.ini. `UMvsSettingsSubsystem` is the model: `Preview`,
  `Commit`, `Revert`, `GetSaved`, `HasUnsavedChanges`, and `OnSettingsChanged`.
- The settings screen owns a `USettingsViewModel` (a working copy with Apply / Revert / Defaults), which owns one
  `USettingRowViewModel` per option; each option row binds only its own row.
- Style comes from one place: `FMvsTheme` (palette, panel opacity, motion, text size), from `MvsStyle::Theme(this)` or
  from the settings broadcast. Colours that mean something are palette tokens (`EMvsColorToken`), never literals, so
  colour-blind presets and high contrast keep working. Text that should follow settings is a `UMvsText` with a type
  style; in the widget designer, set its *Mvs: Style* and *Color*.
- Capitals go through `UMvsText` / `MvsText::SetUpperCase` (culture-aware), never Slate's transform policy (German
  "ß" breaks it).
- Screen readers: `MvsAccessibility::SetText` on the Slate widget a reader lands on (buttons, rows, prompts, the custom
  layers).

### Localization (ADR 0006)
- All user-facing text is `FText`: `LOCTEXT` in code, the `MvsClues` string table for clue text.
- `Scripts/Localize.bat` (editor closed) gathers, imports the `.po` files, exports them again with new strings,
  regenerates the en-XA pseudo-locale and compiles `.locres`. Translators edit `Content/Localization/Game/<culture>/Game.po`.
- Text typed into a Widget Blueprint gets a key of its own that no translation has; screens fill such captions from code
  keys instead (`WBP_PauseMenu`'s `ObjectiveLabel` / `EvidenceLabel`).
- `CheckTranslations.py` (the gate's G7) fails on any missing, stale or untranslated entry in de or ja.

### Custom Slate and world overlays
- `SGadgetWheel`, `SComboMeter`, `SClueTile` and the panels paint with custom vertices; each has a `UWidget` wrapper.
  Animation uses an active timer that unregisters when settled; nothing ticks.
- World overlays (clue markers, threat indicators) are one shape: a UMG layer (`UMvsWorldOverlayLayer`) over
  `SMvsWorldOverlay<TItem>`, whose active timer fetches the frame's items and repaints only when they changed or the
  layer animates. Inactive layers cost nothing.

### Gameplay features the UI reflects
- **Forensic Mode:** one eased alpha in `UForensicComponent` drives the post-process (`UForensicVisionComponent`) and
  the UI overlay (`UForensicViewModel`). Clues draw through walls with custom depth and stencil.
- **Threats:** `UMvsThreatSubsystem` runs the thugs with pure rules (`FMvsThugBrain`, `FMvsAttackDirector`) and
  publishes a snapshot per frame; the threat binder forwards it to `UThreatViewModel`, drawn by the threat layer.
- **Case file:** a `UTileView` over `UClueEntryViewModel`s, pooled tiles (`UClueEntryWidget` → one `SClueTile` each),
  a detail pane following selection.

### Ticking
C++-only widgets tick by default; every widget calls `MvsUI::DisableTick(this)` in `NativeConstruct` (screens and
settings-aware widgets already do). The exception is list and tile entries: the engine forces their rows to tick, and
marking them `Never` trips an ensure. Use events, delegates and active timers.

## Common changes

Each recipe ends with the tests to add; the [Designer guide](DesignerGuide.md) covers changes that need no C++ (clues,
gadgets, restyling, settings, actions, languages).

### Show a new gameplay value on the HUD
1. Add a delegate to the component (gameplay never includes UI).
2. Add the field to the feature's view model (`FieldNotify`, getter, `UE_MVVM_SET_PROPERTY_VALUE`), or create a new view
   model and binder (derive `UMvsViewModelBinder`: create its view models in `Initialize(ULocalPlayer&)` with
   `AddViewModel<T>()`, which registers them where the subsystem and the resolver find them, and add `AddBinder<...>()` in `UMvsViewModelSubsystem::Initialize`).
3. In the binder's `Bind(AMvsCharacter&)`, subscribe through `FMvsSubscriptions` (removed on `Unbind`) and push the
   current value immediately (components have a `BroadcastCurrent`-style call for this).
4. In the widget, `MvsMVVM::Bind` the field in `NativeConstruct`, `Unbind` in `NativeDestruct`, style from the theme.
5. Tests: the view model's behaviour in an editor test (construct it directly); the binder with a component driven
   through its `Advance`-style entry point if it has rules.

### Add a screen
1. Derive `UMvsScreen`; build the tree in `RebuildWidget` (guard with `if (!WidgetTree->RootWidget)`), bind view models
   in `NativeConstruct`, set `DefaultFocus`, add `MakeActionBar` labels.
2. Add a `TSoftClassPtr` setting for it in `UMvsUISettings` (and to `GetPreloadPaths`), with its C++ class as default.
3. If a key opens it, add a row to `UMvsUISettings::GetShortcuts` (the action must exist in the action table). Nothing
   else needs to know the feature.
4. Tests: a functional test in `MVVMSampleTests` using `MvsMenuTestKit.h` (open it, keys, focus, prompt clicks, close);
   if it has a key, `Mvs.UI.Shortcuts` checks the table.

### Add a setting or a rebindable action
Follow the [Designer guide](DesignerGuide.md#add-a-setting); the settings table and the action table are the single
places to edit, and existing tests check every setting has a tab, a label and a description.

### Add user-facing text
`LOCTEXT` with the file's namespace; run `Scripts/Localize.bat`; translate the new entries in the de and ja `.po`
files (the gate's G7 fails until you do).

### Add a dev flag
Under `#if !UE_BUILD_SHIPPING` in `Core/MvsDevAids.cpp`, parsed as `-Mvs<Name>`, scheduled on the dev aid's timeline
(`FMvsScript`). Document it in the README's dev-flag list. Flags that open screens must not open one before the screen
classes have preloaded (the dev aid flushes the preload first for that reason).

### Add a perf scenario
In `Core/MvsPerfHarness.cpp`, **at the end, before `no-ui-paused`**: the world keeps running under menus, so a scenario
inserted earlier shifts every later one onto a different moment of the scene and changes their numbers. Give it a
validity check (`Check`), a budget in `Scripts/PerfBudgets.json` (the gate fails a scenario without one), and add it to
`Scripts/ProfileUI.ps1`'s default list. A screen pushed while the same screen is still closing becomes a second
instance; push from a clean state.

### Replace a code-built screen's content with a designer's Widget Blueprint
The worked example is `WBP_PauseMenu`; the step-by-step is in the [Designer guide](DesignerGuide.md#build-a-screens-content-in-the-widget-designer-wbp_pausemenu)
and the costs in [ADR 0008](ADR/0008-manual-view-model-subscriptions.md).

## Tests

| Kind | Where | Runs in | Use for |
|---|---|---|---|
| Unit / spec (`Mvs.*`) | `Source/MVVMSampleTests/Private/*Tests.cpp` | Editor pass, headless | View models, pure rules, settings, palette, input tables, Slate maths, scripts |
| Functional (`Mvs.Functional.*`) | `Functional*Tests.cpp` + `MvsMenuTestKit.h` | Game pass, small game window | Focus, hit-testing, prompt clicks, toggle keys, live restyle: one test per screen |
| Characterization | `CharacterizationTests.cpp` | Editor pass | Pinning names and defaults that saved data depends on |

- Rules worth testing live in UObject-free code or behind an `Advance(DeltaTime)` entry point (ADR 0004).
- A functional test is a script: `MvsMenuTest::Run(this, TEXT("Name"), &Body)`; the body adds steps (`Do`, `WaitUntil`,
  `Check`) to an `FMvsScript`. Each test starts and ends with no menu open and the settings reverted, so any one runs
  alone. Input goes through `FSlateApplication` (never OS input); `AddClick` makes a real move-press-release click.
- A rule that needs a precondition says so in its text ("(precondition)") so a failure reads as setup, not as the rule.

## Verifying a change: the gate

```bash
powershell -ExecutionPolicy Bypass -File Scripts/Verify.ps1
```

Close the editor and leave the machine idle while it runs (the functional tests and the perf runs are sensitive to
other load). It prints one line per check and writes a report to `Saved/Verify/<timestamp>.md`.

| Check | What | Fails when |
|---|---|---|
| G1 | Clean rebuild of the editor target | Any project warning or error |
| G2 | All tests, editor and game pass | Any failure |
| G4 | 20 screenshots via dev flags, diffed against `Docs/img` | An image changes beyond its noise threshold (`Scripts/ScreenNoise.json`) |
| G5 | Perf: the current build and the reference (master) built in `Saved/PerfCur` / `Saved/PerfRef`, 6 rounds in alternating order | A scenario's median of order-balanced pairs is over +0.05 ms, or its UI cost is over its budget, or a scenario was not in the state it measures |
| G6 | Every log written during the run | An ensure, a `LogMvs*` warning or error, or a content-integrity warning |
| G7 | Translations | A missing, stale or untranslated de / ja entry |

- **Time:** about 30 minutes in full; G5 is about 24 of them. G4 and G5 are skipped automatically when nothing that can
  change their result differs from master (test-only code never counts); the gate prints its decision first, and
  `-ForceScreens` / `-ForcePerf` run them anyway. `-Quick` builds incrementally and skips perf; `-Only G2,G4` runs a
  subset. Pass a list from a PowerShell prompt (`.\Scripts\Verify.ps1 -Only G2,G4`) or through `-Command`:
  through `powershell -File`, `G2,G4` arrives as one string, matches no check, and the gate "passes" having run
  nothing.
- **Commit before G5.** The perf worktrees take tracked changes from your working copy but not untracked files, so a new
  asset that is not committed is missing from the measured build.
- **A screenshot changed on purpose:** look at the `*.diff.png` in `Saved/Verify/Screens`, and if the change is intended,
  recapture the baseline (`Scripts/CaptureScreens.ps1 -Only <name>` writes to `Docs/img`) and say why in the commit.
- **A perf result you do not believe:** run `Verify.ps1 -Only G5 -PerfRef HEAD -ForcePerf` (the build against itself must
  pass) and `Scripts/ProfileUI.ps1 -Scenarios <name> -All` for a timer-by-timer breakdown with Unreal Insights. Single
  sessions vary by about ±0.05 ms; trust the gate's paired rounds. [Performance](Performance.md) has the method, the
  budgets and every past measurement.

### Branches and commits
- One branch per piece of work; the gate passes before it merges, and merges fast-forward into `master`.
- Commit messages say what changed and why, and record the gate result; when a measurement or a theory turned out
  wrong, say so in a later commit or the docs rather than rewriting history.
- Every source file starts with `// Copyright IG. All Rights Reserved.` (scripts: `#` / `rem`). Text files are stored
  with the line endings `.gitattributes` sets (CRLF for code and docs); let Git normalize them rather than converting
  by hand.

## Conventions in brief

The full list is in the [Coding standard](CodingStandard.md). The ones reviews catch most often:

- `Mvs` prefix on every project type, log category, test and dev flag; Epic prefixes (`U`, `A`, `F`, `E`, `I`, `S`, `T`);
  assets `WBP_`, `M_`, `MI_`, `DA_`, `L_`.
- No gameplay include in UI code, no widget or world reference in a view model, no literal colour with meaning, no
  `Tick` in widgets.
- Layout numbers that recur go in `MvsMetrics`; text goes through `UMvsText`.
- Reflection into engine internals only in the three documented places, looked up through `Core/MvsEngineProperties.h`.
- Dev-only code under `#if !UE_BUILD_SHIPPING`, switched on by a `-Mvs...` flag.
- Measure before optimizing, and write down the result in `Performance.md`, including what did not help.

## Things that have bitten us

Each of these cost a debugging session; most now have a test or a comment at the spot.

| Symptom | Cause | Where it is handled |
|---|---|---|
| A reopened screen lost its tabs | Common UI's tab list removes its tabs when destructed, which happens when a screen closes back onto another | `UMvsTabList` re-registers on construct |
| A list entry trips "mismatching tick states" | The list forces entry rows to tick; an entry marked `Never` contradicts it | List entries do not call `DisableTick` |
| German capitals stay lower-case and an ensure fires | Slate's upper-case transform cannot change string length ("ß" → "SS") | `UMvsText` upper-cases the `FText` |
| A Widget Blueprint text shows English in every language | Text typed in a Widget Blueprint gets its own localization key | Fill captions from code keys |
| A screenshot run loads a screen class on the spot | A dev flag opened a Widget Blueprint screen before the preload finished | The dev aid flushes the preload first |
| A screenshot differs because of where the mouse is | The game window opens under the real cursor | `-MvsIgnoreHover`; every hoverable widget checks `MvsUI::HoverEnabled()` |
| A perf scenario's numbers move when another scenario is added | The world keeps running, so order changes what each scenario sees | New scenarios go last |
| A perf scenario never reaches its state | Toggling a screen that is still closing closes it instead; pushing it then creates a second instance | Scenarios push from a clean state and check validity |
| G5 cannot find an asset | Untracked files are not copied into the perf worktrees | Commit before G5 |
| The gate passes in seconds with an empty report | `-Only G2,G4` through `powershell -File` arrives as one string | Run from a PowerShell prompt or through `-Command` |
| A binding compiles with "not writable at runtime" | The View Binding targets the widget, not its `Text` property | Bind `Widget.Text` (or `SetText`) |
| Arrow-key navigation searches at an offset in a windowed game | A known engine issue in windowed mode; fullscreen is unaffected | Not worked around |

## Glossary

| Term | Meaning |
|---|---|
| Binder | A `UMvsViewModelBinder` subclass: subscribes to one feature's components and feeds its view models |
| Field notify | The MVVM plugin's per-property change notification (`UE_MVVM_SET_PROPERTY_VALUE`) |
| Layer | One of the four activatable stacks: Game, GameMenu, Menu, Modal |
| Shortcut | A row of `UMvsUISettings::GetShortcuts`: a gameplay action that opens a screen |
| Theme | `FMvsTheme`: the resolved look of the current settings |
| Token | An `EMvsColorToken`, a colour by meaning, resolved per palette |
| Dev aid / dev flag | A `-Mvs...` command-line switch that stages a state for screenshots or demos (non-Shipping only) |
| Script | An `FMvsScript`: a list of timed steps on the core ticker, used by dev aids, the perf harness and functional tests |
| UI cost | A perf scenario's game-thread time minus the matching no-UI reference from the same run |
| The gate | `Scripts/Verify.ps1`: what must pass before a merge |
